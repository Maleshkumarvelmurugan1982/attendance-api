# REVIEW.md

Review of the starter `app/main.py`. Line numbers refer to the **original** starter file.

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | Module setup, l.22 | `MongoClient(...)` without `tz_aware=True`: every datetime read back is **naive**, so comparing it with an IST/UTC-aware value raises `TypeError`, and `.date()` on it gives the UTC date. | Punch-out compares the stored `punch_in` with an aware `shift_end` -> 500. | `MongoClient(MONGO_URI, tz_aware=True, serverSelectionTimeoutMS=3000)`; all instants handled as aware UTC. |
| 2 | Module setup, l.22-23 | Connection string falls back to a hard-coded `mongodb://localhost:27017`; no server-selection timeout, so a dead DB makes requests hang ~30 s. | Start without `MONGO_URI`: app silently talks to a local DB. Stop Mongo: `/health` hangs instead of answering. | `MONGO_URI` is required (clear startup error if missing); `.env` loaded with `override=False` so real env vars win; 3 s timeout. |
| 3 | Whole file | **No indexes are created.** Uniqueness of `emp_code` and of (`emp_code`, `date`) is never enforced, and every list/analytics query is a collection scan. | `explain` shows `COLLSCAN`; slow at 100k records; duplicates possible (see #10, #17). | `ensure_indexes()` at startup (idempotent): unique `emp_code`, unique (`emp_code`,`date`), plus indexes for each list/analytics query. |
| 4 | `health`, l.72-74 | Always returns 200 without touching MongoDB. | Stop MongoDB -> `/health` still 200 (contract: 503). | `ping` the server; 503 on failure (and retry index creation if startup could not). |
| 5 | `compute_late_minutes`, l.35 | Builds shift start with `punch_in.replace(hour=h, minute=m)` in whatever zone `punch_in` is in (naive server-local / UTC), not IST. | Server in UTC, punch 09:45 IST (04:15 UTC): start becomes 09:30 **UTC** -> late 0 instead of 15. | Shift start built from the attendance date + `shift_start` in IST (`shift_bounds`). |
| 6 | `compute_late_minutes`, l.36-37 | Grace check is done on minutes **after** truncating: `int(630 s / 60) = 10`, `10 > 10` is false. | Shift 09:30, punch 09:40:30 -> 0; contract says strictly more than 10:00 is late -> 10. | Compare elapsed **seconds** `> 600`, then `floor(seconds / 60)`. |
| 7 | `compute_late_minutes` / `punch_in`, l.35, l.102 | Overnight shifts not handled; instants not truncated to whole seconds (R1). | Shift 22:00-06:00, punch 00:30: start = same day 22:00 -> negative -> 0 instead of 150. Punch 09:40:00.900 should count as 09:40:00. | Attendance date per R1 (previous day when before `shift_end`), shift start on that date; `ms_to_dt` truncates to seconds and the truncated value is stored. |
| 8 | `compute_work_hours`, l.41 | `round(x, 2)` is binary-float, banker's-style rounding, not half-up (R4). | 32 850 s = 9.125 h -> `round` gives 9.12, contract 9.13. | Exact `Decimal(seconds)/3600` quantized `ROUND_HALF_UP`; half day compares the rounded value (R5). |
| 9 | `compute_overtime`, l.44-47 | No 30-minute minimum (R3); for an overnight shift the end is put on the start date; compares an aware datetime with a naive one. | 5 min late leaving -> 5 instead of 0. Overnight 22:00-06:00 punch-out 06:40 next day -> ~24 h of overtime. Naive `punch_out` -> `TypeError` 500. | Shift end on the next day for overnight shifts; `floor(min)` counted only when `>= 30`; all aware datetimes. |
| 10 | `create_employee`, l.79-83 | Check-then-insert: two parallel creates both pass `find_one` and both insert. | 20 parallel `POST /employees` with the same code -> several 201s, duplicate employees. | Unique index on `emp_code`; just `insert_one` and map `DuplicateKeyError` -> 409. |
| 11 | `create_employee`, l.82, l.85 | `created_at = datetime.now()`: naive **server-local** time stored as if UTC; returned as an ISO string, not epoch ms. | Server in IST: `created_at` 5 h 30 off. Response `"created_at": "2026-..."` fails the schema (integer). | `datetime.now(timezone.utc)` (ms precision), returned as epoch ms. |
| 12 | `EmployeeIn`, l.53-60 | No validation: any `emp_code`, email, department length, `HH:MM`, `joined_on`; `shift_start == shift_end` accepted. | `{"emp_code": "x", "shift_start": "25:99", "joined_on": "yesterday"}` -> 201 (contract: 422). | Pydantic constraints from the schema (`^EMP[0-9]{4,6}$`, lengths, email, `HH:MM`, real calendar date) + validator for equal shift times. |
| 13 | `list_employees`, l.93 | `skip = page * page_size` skips the whole first page. | `page=1` returns employees 21-40. | `skip = (page - 1) * page_size`. |
| 14 | `list_employees`, l.94 | `total` counts the whole collection, ignoring the `department` filter (R10). | `?department=Sales` -> `total` equals all employees. | `count_documents(q)` with the same filter. |
| 15 | `list_employees`, l.89, l.95 | No sort (contract: by `emp_code`), no bounds on `page`/`page_size`. | Order changes between calls; `page=0` -> negative skip -> 500; `page_size=0` -> `limit(0)` returns everything; `page_size=1000` accepted. | `.sort("emp_code")`; `page >= 1`, `1 <= page_size <= 100` -> otherwise 422. |
| 16 | `punch_in`, l.101, l.113 | Employee lookup result never checked. | Unknown `emp_code` -> `emp["shift_start"]` on `None` -> 500 (contract: 404). | 404 when the employee does not exist. |
| 17 | `punch_in`, l.104-118 | Check-then-insert race on (`emp_code`,`date`). | 2 identical parallel punch-ins -> both 201, two records for one day. | Unique (`emp_code`,`date`) index; `DuplicateKeyError` -> 409. |
| 18 | `punch_in`, l.102-103 | `datetime.fromtimestamp(ms/1000)` uses the **server's** time zone, and `date` is taken from that (and from UTC on most servers), not IST (R1). | Server in UTC, punch 00:30 IST on 8 Jul -> `date` 2026-07-07. | Convert to aware UTC, compute the IST attendance date with the overnight rule. |
| 19 | `PunchInIn`, l.63-66 | `punched_at: Optional[int]` in lax mode accepts `1783312500000.0` and `"1783312500000"`; seconds-looking and out-of-range values pass; `status` accepts any string (`ABSENT`, `HOLIDAY`). | `{"punched_at": 1783312500}` (seconds) -> record in 1970 + 201. | `Strict` int with `ge=100000000000, le=4102444800000`; `status: Literal["PRESENT","WFH","ON_DUTY"]`. |
| 20 | `punch_in` l.119-121, `list_attendance` l.149 | Responses add `"id"` (the `_id`), return datetimes instead of epoch ms; legacy records without `history`/`half_day` come back without those fields. | Response keys differ from `AttendanceRecord`; `punch_in` is an ISO string. | One serializer `record_out()`: exact contract fields, epoch ms (also inside `history[].changes`), defaults for missing fields. |
| 21 | `list_attendance`, l.144-147 | Loads the **entire** filtered collection into Python, sorts and slices in memory. | 100k records: seconds per request and memory spikes; `explain` = `COLLSCAN`. | `find(filter).sort().skip().limit()` backed by indexes; `count_documents(filter)` for `total`. |
| 22 | `list_attendance`, l.145 | Sorted only by `date` desc; ties on the same date in arbitrary order (contract: then `emp_code` asc), so pages can repeat/skip rows. | Two pages of a busy day overlap. | Sort `[("date", -1), ("emp_code", 1)]`. |
| 23 | `list_attendance`, l.125-131 | No validation of `date_from`/`date_to` format, `date_from > date_to`, `status`, `page`, `page_size`. | `?date_from=2026-13-01` or `?status=HOLIDAY` -> 200 with nothing; `page=0` -> wrong slice. | Validated date strings, `Status` enum, page bounds, `date_from > date_to` -> 422. |

**Looked at and decided it is fine**

* `load_dotenv()` (l.20): default `override=False`, so real environment variables already win over `.env` - kept, made explicit.
* `IST = timezone(timedelta(hours=5, minutes=30))` (l.25): correct fixed offset; India has no DST.
* `status_code=201` on the two POST routes (l.77, l.99): matches the contract.
* Building the `date` range filter with string `$gte`/`$lte` (l.136-141): correct, because `YYYY-MM-DD` strings sort chronologically; kept.
* `doc.pop("_id", None)` in `create_employee` (l.84): needed because `insert_one` adds `_id` to the dict; kept (now inside the serializer).
* Synchronous `def` endpoints: FastAPI runs them in a thread pool and `MongoClient` is thread-safe, so concurrency is handled by the database (unique indexes, conditional updates), not by the event loop.
